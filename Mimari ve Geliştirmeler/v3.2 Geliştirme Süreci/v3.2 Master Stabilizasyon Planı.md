## 0. Yönetici Özeti

### 0.1 Genel tablo
Projenin iş mantığı ve özellik vizyonu güçlü: V2 alt-koleksiyon veri modeli, Pub/Sub (`onInventoryDataUpdated`), atomik stok transaction'ı, ENV_GUARD, touch-first FAB/Bottom Sheet, ITSM zimmet zinciri, EBYS durum makinesi ve VIP paneli doğru fikirler üzerine kurulu. Ancak denetim **129 bulgu** ortaya çıkardı (30 Kritik / 44 Yüksek / 40 Orta / 15 Düşük-Latent). Bunların büyük kısmı birbirinden bağımsız hatalar değil; **7 sistemik kök nedenin** (§2) farklı dosyalardaki yansımaları. En önemlisi: sistemde "kim giriş yaptı?" sorusunun tek bir cevabı yok ve modüllerin hangi sırayla, kaç kez yüklendiği deterministik değil. Biyometrik özellik `activeUser` saklama biçimini değiştirdiğinde onu okuyan 12 yer sessizce kırıldı; ESM geçişi talep kayıt fonksiyonunu ve kart görünümünün başlatma kodunu kaybetti; soft-logout, sayfa yenilenmeden yeniden girişte tüm modalları görünmez bıraktı. Walkthrough'larda "tamamlandı" işaretli en az 15 özellik bugün çalışmıyor (§3.2).

### 0.2 🚨 Bugün yapılması gerekenler (kod dışı, dakikalar sürer)
1. **Admin şifresini değiştirin** (Firebase Console → Authentication → `admin@medipol.local`). Son hosting deploy'u `backup/functions/index.js` dosyasını (ADMIN_HASH + SALT) herkese açık yayınlamış; 5 haneli bir şifre bu bilgilerle saniyeler içinde kırılır (SEC-02). Arayüz şimdilik 5 haneyle sınırlı olduğu için farklı bir 5 haneli kod seçin; uzun şifre desteği Faz 4.4'te.
2. **VIP → "Tekerrürleri Temizle" butonunu kullanmayın.** B3 hareket defterinde aynı seri numaralı kayıtların en yenisini — çoğunlukla aktif zimmeti — siliyor (VIP-01).
3. **localhost'tan kill switch / force logout / sistem mesajı test etmeyin.** `system_config` ortam ayrımı yapmıyor; testler canlı kullanıcıları etkiler (RULE-04).
4. **Yeniden deploy etmeden önce Faz 0.2'yi okuyun.** Canlıdaki sürüm (01.07.2026) yereldeki koddan eski; mevcut yerel kodu olduğu gibi deploy etmek bugün çalışan bazı akışları da kırabilir.

## 2. Kök Neden Analizi

Bulguların büyük kısmı aşağıdaki yedi sistemik kök nedenin farklı yerlerde tekrar eden belirtileridir. Planın mantığı bu yüzden "tek tek hata kapatmak" değil; önce bu kök nedenleri kurutmak (Faz 1 ve 3), sonra kalan yerel hataları kapatmak.

### KN-1 · Tek bir "kimlik" kaynağı yok
Aynı kullanıcıyı temsil eden dört ayrı kaynak var ve her modül farklı birini okuyor:
1. Firebase Auth oturumu (`window.userAuth`) — personel için daima **anonim**, admin için e-posta oturumu.
2. `localStorage.activeUser` — biyometrik özellikle **maskeli (XOR+base64)** yazılmaya başlandı.
3. `window.currentUser` — yalnız index.html'de set ediliyor; admin.html'de hiç.
4. İsim karşılaştırması (`'Muhammed Cer' || 'Admin'`) — "UI admin"ini belirliyor.

Biyometrik özellik `activeUser` biçimini değiştirdiği anda formatı bilmeyen 12 okuyucu sessizce `null` almaya başladı (AUTH-01). "Zero-Trust" sprinti `isAnonymous` kontrollerini UI koduna kopyaladığında personelin TODO modülü kapandı (TODO-01). `checkIsAdmin()` anonim oturumu da admin saydığı için UI'daki tüm yetki kapıları herkese açık (AUTH-02).
**Çare:** Tek Session Store (formatı yalnız o bilir) + iki ayrı ve açık kavram: `isAppLoggedIn()` (kodla giriş yapmış kişi) ve `isDbAdmin()` (Firebase admin oturumu). → Faz 1.2-1.4

### KN-2 · Modül grafiği deterministik değil
- Klasik `<script>` dosyaları, kaynaktaki sıralarından bağımsız olarak **tüm modüllerden önce** çalışıyor (ARC-05).
- Aynı modül farklı URL ile (query'li/query'siz) yüklenince tarayıcı onu **iki kez** çalıştırıyor: index'te 6 modül, admin'de Firebase katmanı (ARC-01/02). Kaynağı elle eklenen `?v=` ve `cache-buster.js`.
- Aynı global adı birden çok dosya tanımlıyor ve çoğu durumda yanlış olan kazanıyor (ARC-06, EBYS-01, ADM-03).
- admin.html ortak modüllerin çoğunu yüklemiyor, köprüler orada no-op; canlı veri yönlendiricisi yalnız index'te (ARC-03/04).
**Çare:** Sayfa başına tek giriş modülü, her modül tek URL, global ad tekilliği, ESM ile uyumlu önbellek stratejisi. → Faz 1.1, 1.6, 6

### KN-3 · Kayıt katmanı "başarısız olamaz" gibi davranıyor
- `saveData` hataları yutuyor ve oturum yoksa sessizce dönüyor → her çağıran "başarılı" gösteriyor (DATA-02).
- `saveData` hedef koleksiyonun **tamamını** her seferinde yeniden yazıyor; 28 yerde tüm veritabanını yazan `saveData(window.data)` var (DATA-01). Spark kotası bu desenle çok hızlı tükenir ve kota bitince tüm yazmalar gün sonuna kadar sessizce başarısız olur.
- Tam kayıt, personel oturumunda ilk paket (b1) reddedildiği için **hiçbir şeyi** kaydetmiyor (DATA-03).
**Çare:** Hedefli/tek-doküman yazma (Faz 2), değişiklik tespitli ve hata fırlatan veri API'si (Faz 3.1-3.2).

### KN-4 · İş kuralları UI'da, yetki kuralları Firestore'da — ve birbirlerini tanımıyor
Firestore kuralları personelin b1/b2/b3'e yazmasını yasaklıyor; UI ise personelin sarf çıkışı yapabileceğini ve "Teslim Aldım" ile zimmet kaydı yazabileceğini varsayıyor (RULE-01). Tersine, kod girmemiş herhangi bir ziyaretçi talepleri/görevleri/satın almaları yazıp silebiliyor ve tüm oturum kodlarını okuyabiliyor (RULE-02). Bazı özellikler kuralı hiç olmayan root yollara yazıyor (RULE-03).
**Çare:** Özellik × rol × koleksiyon yetki matrisi (Ek D); kurallar ve UI kapıları aynı matristen türetilir. → Faz 4

### KN-5 · İndeks tabanlı işlem + her snapshot'ta yeniden oluşturulan diziler
`window.data[col]` her Firestore snapshot'ında yeni bir diziyle değiştiriliyor; silme, düzenleme, onay, sepet, zimmet atama gibi işlemler ise bir önceki render'da yakalanan **dizi indeksiyle** çalışıyor. Başka bir kullanıcının eklediği tek bir kayıt, yanlış ürünün silinmesine/düşülmesine yol açabilir (DATA-06). `saveProduct` ve `editPersonel` kaydın id'sini düşürdüğü için her düzenleme dokümanı silip yeniden oluşturuyor (DATA-04).
**Çare:** Tüm işlemler `id` ile; güncelleme her zaman mevcut kaydın üzerine birleştirilerek. → Faz 2 (tehlikeliler), 3.3

### KN-6 · Şema sözleşmesi yok
B3 kayıtları üç farklı şemayla yazılıyor; durum `durumu`/`status`, ürün `ürün`/`name`/`urunAciklama`, kişi `personel`/`alanKisi`/`person` diye dağılmış; `runStockTransaction` her stok hareketinde manuel durumu eziyor; dört farklı demirbaş sınıflandırıcısı var (DATA-05, DATA-08, INV-08). Her yeni ekran kendi okuma varsayımını yaptığı için tablolar boş kolon, KPI'lar çift sayım gösteriyor.
**Çare:** Kanonik şema + tek normalizer + tek seferlik göç. → Faz 3.5-3.6

### KN-7 · Geçişlerde kaybolan davranışlar fark edilmiyor
ESM geçişinde `saveRequest` tamamen kayboldu (ITSM-01), kart görünümünün başlatma kodu kayboldu (INV-03), `pageshow` gibi eski handler'lar yeni auth akışıyla çakışır halde kaldı (UI-01), soft-logout modalları kalıcı gizledi (UI-02), self-approval'ın "Güvenlik Raporu" butonu hiç çağrılmayan bir sarmalayıcıya bağlandı (EBYS-05). Walkthrough'lar "doğrulandı" diyor ama tekrarlanabilir bir regresyon listesi veya smoke test yok; proje git deposu da değil (OPS-01); PowerShell'le yazılan dosyalar karakter kodlamasını bozdu (VIP-09).
**Çare:** git + her faz sonunda aynı regresyon listesi + konsol-hatası smoke testi + Emulator'de kural testleri + süreç kuralları (§8). → Faz 0, 7

## 8. Süreç Önerileri

Bu projedeki regresyonların önemli bir kısmı koddan değil süreçten kaynaklanıyor (KN-7). Ajan talimatlarına şu kuralların eklenmesini öneriyorum:

1. **git zorunluluğu:** Her görev ayrı commit; walkthrough'ta commit hash'i ve değişen dosya listesi.
2. **"Tamamlandı" tanımı:** Kod değişikliği + Ek A'daki ilgili maddelerin **gözlenmiş** sonucu + smoke testin temiz çıkması. "Doğrulandı" demek için konsol çıktısı veya ekran görüntüsü gibi kanıt gerekir.
3. **Karakter kodlaması (OPS-03, VIP-09):** Windows PowerShell 5.1'de `Set-Content`/`Add-Content`/`Out-File` ile kaynak dosya yazmak yasak (veya `-Encoding utf8` zorunlu); tercihen editör araçları. Regex ile toplu değişiklikte önce önizleme.
4. **Global ad kuralı:** Yeni bir `window.X` eklemeden önce proje genelinde arama; aynı adın ikinci tanımı yasak.
5. **Maskeleme çiftleri kuralı:** Bir hatayı düzeltmek bir başka hatanın önünü açıyorsa (§5.0), ikisi aynı commit'te ele alınır.
6. **Anayasa'ya önerilen ekler:**
   - `localStorage.activeUser`'a doğrudan erişim yasak; yalnız Session Store.
   - `saveData(window.data)` (tam kayıt) yasak; hedefli veya tek-doküman yazma zorunlu; `saveData` sonucu kontrol edilir.
   - Kayıtlar dizi indeksiyle değil `id` ile hedeflenir; güncelleme mevcut kaydın üzerine birleştirilerek yapılır.
   - `innerHTML`'e giden her dinamik değer `escapeHtml`'den geçer.
   - Aynı modül tek URL ile yüklenir; `?v=` query kullanılmaz.
   - `system_config` dahil tüm Firestore yolları `window.AppEnv.COLLECTION_ROOT` üzerinden kurulur.
7. **Rol dağılımı (mevcut `agent-roles.md` ile uyumlu):** Faz 1.1/1.6 ve Faz 3 → Master Architect (Orchestrator + `/services`); Faz 1.2-1.4 → Master Architect + Algorithmic Chef; Faz 2 görünüm kısımları → UI yürütücü; Faz 4.2 kuralları ve tüm fazların denetimi → Security Auditor; uygulama → Local Executor.

## Ek C — Firestore Rules v2 Taslağı

**Aşama A** — bugünkü anonim modelle uyumlu sıkılaştırma. Önce Emulator'de test edilir; Faz 2.5'teki `system_config` taşımasıyla birlikte yayınlanır.

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    function signedIn()  { return request.auth != null; }
    function isAdmin()   { return signedIn() && request.auth.token.email == 'admin@medipol.local'; }
    function validRoot(r){ return r in ['inventory_v2', 'inventory_demo']; }

    function maintenanceOn(r) {
      return exists(/databases/$(database)/documents/$(r)/system_config/items/admin_settings)
        && get(/databases/$(database)/documents/$(r)/system_config/items/admin_settings)
             .data.get('maintenance', false) == true;
    }

    // XSS savunma derinliği: etiket benzeri "<harf", "</", "<!" reddedilir ("<5mm" gibi metinler serbest)
    function noTag(v) { return !(v is string) || !v.matches('(?s).*<[a-zA-Z/!?].*'); }
    function textOk(d) {
      return noTag(d.get('personel', '')) && noTag(d.get('ürün', '')) && noTag(d.get('urun', ''))
          && noTag(d.get('not', ''))      && noTag(d.get('aciklama', '')) && noTag(d.get('title', ''))
          && noTag(d.get('description', ''));
    }

    match /{root}/{col}/items/{docId} {
      allow read: if validRoot(root) && signedIn();

      // Admin: tüm koleksiyonlar (system_config/items dahil)
      allow write: if validRoot(root) && isAdmin();

      // Personel (Aşama A'da anonim oturum): yalnız iş akışı koleksiyonları
      allow create, update: if validRoot(root) && signedIn() && !isAdmin()
        && col in ['purchaseOrders', 'requests', 'tasks']
        && !maintenanceOn(root)
        && textOk(request.resource.data);

      // Silme: personel yalnız görev silebilir; talepler ve satın almalar admin'e ait
      allow delete: if validRoot(root) && signedIn() && col == 'tasks' && !maintenanceOn(root);
    }

    // Geçiş dönemi: eski root system_config (taşıma tamamlanınca kaldırılır)
    match /system_config/{doc} {
      allow read: if signedIn();
      allow write: if isAdmin();
    }

    // V1 arşiv kilidi
    match /inventory/{document=**} { allow read, write: if false; }
  }
}
```
> **Uyarı:** `assignments` ve `serviceRecords` bugün yalnız admin tarafından yazılıyor; Aşama A'da personel listesinden çıkarılmaları gerekir. Bu değişiklik Faz 2.6'daki zimmet akışlarının admin oturumunda çalıştığı doğrulandıktan sonra yapılmalıdır.

**Aşama B** — personel başına Firebase Auth hesabı (K4) sonrası, Faz 3.1-3.2 tamamlandıktan sonra (özet):
```
function isStaff() { return signedIn() && request.auth.token.firebase.sign_in_provider != 'anonymous'; }
function isOwner(d) { return d.get('personelUid', '') == request.auth.uid; }

match /{root}/requests/items/{id} {
  allow read:   if isStaff();
  allow create: if isStaff() && isOwner(request.resource.data) && textOk(request.resource.data);
  allow update: if isAdmin() || (isStaff() && isOwner(resource.data)
                   && request.resource.data.diff(resource.data).affectedKeys()
                        .hasOnly(['durum', 'tarih', 'ürün', 'adet', 'not', 'talepTuru', 'oncelik', 'iadeTarihi']));
  allow delete: if isAdmin();
}
// purchaseOrders: onay yalnız workflow.steps[currentStep].userUid == request.auth.uid ise, vb.
// personel koleksiyonu: yalnız admin okur/yazar; kodlar Auth'a taşınır.
```
